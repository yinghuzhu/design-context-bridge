# 多模态视觉与业务验证

CLI 只准备和校验确定性设计上下文，CLI 不做图片识别、像素或语义评分，也不产生视觉通过结论。必须由具备图片理解能力的多模态 Agent 同时查看 Figma 原稿截图和目标应用的实际截图，理解差异、定位可能代码原因并迭代修正。

## 建立可比证据

每个必须交付的页面和状态都要准备一对可追溯证据：

- 原稿截图：使用 `manifest.json` 声明的根 screenshot 路径，不假定文件一定是 PNG。
- 实际截图：来自真实启动的目标应用和目标路由，不使用 `reconstruct.html`、静态 DOM 或组件预览替代。

两张截图必须对应相同目标条件：

- 同一 `viewport` 宽高和目标响应式断点；
- 记录并保持一致的 `device pixel ratio`；
- 同一页面状态，例如 default、loading、success、empty、error、hover、focus 或 disabled；
- 相同且稳定的内容数据，包括文案、数量、图片、权限和 locale；动态时间、动画、随机数据应冻结或在记录中解释。

如果原稿未提供某个交互状态，不得凭空声称已对该状态视觉验收；根据用户要求和既有业务语义实现，并把缺少视觉来源记录为限制。

## 多模态检查清单

多模态 Agent 必须实际查看每一对图片，并逐项检查：

- 页面结构、区块顺序和信息层级；
- 几何尺寸、位置、对齐和响应式布局；
- 间距，包括 padding、gap、margin 和密度；
- 字体、字号、字重、行高、字距和换行；
- 颜色、透明度、边框、圆角和视觉效果；
- 阴影、遮罩、叠放关系与层级；
- 图片、图标、背景等素材的正确性、比例、定位和清晰度；
- overflow、圆角蒙版、object-fit 等裁剪行为；
- Figma 或用户要求状态，包括 hover、focus、disabled、loading、empty、error 和成功态。

不得以肉眼一句“基本一致”、CLI 输出、文件完整性或自动图片评分替代上述检查。

## 差异记录与修复循环

每个发现都记录以下字段，证据路径使用相对路径且不得包含凭据：

| field | 内容 |
|---|---|
| `area` | 页面区域、组件或状态 |
| `severity` | `high`、`medium` 或 `low` |
| `expected` | 从原稿及节点数据观察到的预期 |
| `actual` | 实际运行截图中的结果 |
| `likely cause` | 最可能的组件、样式、数据或环境原因 |
| `evidence path` | 原稿截图、实际截图或检查记录的相对路径 |

严重度按用户可见影响判断：阻断页面识别、关键内容/操作或主要结构为 `high`；明显几何、排版、素材、状态偏差为 `medium`；不妨碍使用且难以感知的微小偏差为 `low`。

执行循环：

```text
获取同条件截图
  -> 多模态 Agent 记录差异与原因
  -> 定向修改相关代码
  -> 运行必要的快速检查
  -> 重启或刷新真实页面并重新截图
  -> 再次多模态检查
```

重复到所有要求页面和状态都没有未解决的**高、中优先级**视觉问题。低优先级差异可以保留，但必须在最终报告逐项说明；若多轮没有实质进展，按设计方案报告阻塞、尝试、根因和所需协助，不能降低门禁。

## 交互与业务回归

视觉门禁通过后，按实际改动范围运行相关检查；对不适用的类别写明原因，不能把“未运行”记成“通过”：

- `build`：生产或目标环境构建；
- `type`：类型检查和编译诊断；
- `console`：目标路由运行时浏览器控制台无本次新增错误；
- `interaction`：按钮、链接、弹窗、表单、键盘和导航；
- `API`：请求方法、URL、参数、响应映射、loading 与成功/失败处理；
- `state`：store、缓存、轮询、状态转换及跨组件同步；
- `validation`：输入限制、提示文本、提交门禁和服务端错误映射；
- `error`：空数据、网络错误、权限过期、重试和降级路径；
- `protected-flow`：用户确认必须保持的路由、支付、预订、结算或其他关键业务流程。

只要修改**可能影响交互或已有业务流程，就必须验证**对应路径和现有相关测试。不能只凭代码审阅推断行为没变，也不能为了让检查通过而修改范围外业务语义。

**视觉通过但业务失败时，禁止更新为 `validated`，禁止通知人工验收。** 修复本次引入的问题后重新执行对应视觉和业务门禁；若失败是可证明的既有或范围外问题，记录证据和阻塞并请求决定，但仍不得宣称完整验收通过。

## 完成门禁与人工交接

只有同时满足以下条件，才能把状态更新为 `validated` 并通知人工验收：

1. 所有要求页面和要求状态都已实现，并取得真实运行实际截图。
2. 多模态 Agent 已查看原稿截图与每张实际截图，未留下 high 或 medium 问题。
3. 相关 `build`、`type`、`console`、`interaction`、`API`、`state`、`validation`、`error` 和 `protected-flow` 检查全部通过或有明确不适用依据。
4. 修改可能影响的交互、已有业务流程和受保护行为均有通过证据。
5. 运行 URL、原稿/实际截图路径、检查结果和已知 low 差异可供人工复查。

完成报告至少包含：目标与模式、运行 URL、原稿截图、实际截图、使用的 viewport/DPR/页面状态/内容数据、多模态检查结论、构建和业务检查、受保护流程结果、低优先级差异与剩余限制。报告措辞是“工具检查已通过，请人工验收”，不能代替人工做最终产品确认。
